# SolidTV 1.7 brief: CPU performance on renderer v2

You are rewriting the internals of `@solidtv/solid` for its next minor release, **1.7.0**, on top of the `v2` branch of `@solidtv/renderer`.

**Goal:** the least CPU per key press, per state change and per text layout on low-end TV hardware, with the fewest breaking changes for apps.

Read this whole brief before you act. It has three parts:

- **What you are optimizing** and the rules you work under: the opening sections, from Priorities to the Compatibility contract.
- **The phases of work**, with two checkpoints where you stop and report to the user.
- **Leads from a read-only survey done on 2026-10-03.** Line numbers drift, so treat every lead as a hypothesis to verify, not a fact.

## Priorities, in order

1. **CPU per key press.** Measure from `keydown` dispatch to the end of the renderer frame that shows the result. That covers:
   - focus-manager dispatch;
   - Row, Column, Grid and Virtual navigation;
   - the focus-path change;
   - `onFocus`, `onBlur` and `onFocusChanged`;
   - applying state styles;
   - flex layout;
   - renderer writes and the frame that follows.
2. **CPU per state change:** `states` add, remove and toggle, `$focus` style apply and undo, `forwardStates`, and transitions.
3. **Text measurement and flex layout of text,** in both Solid and the renderer. Review alternative approaches before choosing one (see the Text measurement and flex layout section).
4. **Allocations per key press, per state change and per text layout.** On TVs, garbage-collection pauses show up as dropped frames. Aim for zero framework allocations in the steady state: allocations made by user handlers and by Solid's own reactivity do not count against this.
5. **Node creation and mount cost.** Virtual lists create nodes as you scroll, so this is on the key-press path for them.
6. **Bundle size:** do not regress it.

Out of scope: new features, pointer or mouse performance (but keep `useMouse` working), the router, and the announcer, except where they sit on the key-press path.

## Hard boundaries

### Renderer changes

You may change only the following.

**The surface Solid touches:**

- node and text-node accessors (`src/core/nodes/Node.ts`, `TextNode.ts`);
- the creation prop bag (`applyProps.ts`, `applyTextProps`);
- `RendererCore` and `Renderer` public members;
- package exports, `index.ts` and `exports/*`;
- events, and `reprocessUpdates`.

**Text measurement:**

- line breaking and measurement in `src/core/text/TextLayout.ts`, including `LayoutCache` and `layoutKey`;
- read access to loaded font descriptions and metrics in `FontRegistry.ts` and `sdfFont.ts`;
- `loaded` delivery for text;
- a new public measurement API.

Examples of what is in bounds:

- a post-creation bulk-set API;
- a public `insertBefore`. Today Solid's `insertChild(before)` cannot reorder renderer siblings, so check whether draw order makes this matter;
- exporting something Solid needs;
- renaming or removing a prop to cut per-write cost;
- a synchronous text-measurement API that fills the same layout cache the walk reads.

### What renderer changes must satisfy

Every renderer change must:

- show a measured win in a Solid benchmark;
- keep `pnpm test` green in the renderer, including:
  - its allocation-budget tests (`src/core/allocation.*.test.ts`);
  - its text-layout tests, which pin 1.10's line breaking;
- respect the renderer `CLAUDE.md` invariants;
- update the renderer's `src/publicApi.test.ts` and `docs/upgrade-1.x-to-2.0.md`;
- be one focused commit.

### What is out of bounds

Out of bounds:

- the `NodeStore` layout;
- the `ScenePass` walk itself;
- the GL backend;
- glyph emission and upload (`TextEmitter.ts`);
- the font atlas and the SDF shader;
- shader compilation and packing;
- texture management.

If a win needs one of these, do not make the change. Write it up in `docs/superpowers/specs/renderer-proposals.md` with the evidence, and move on.

Two known open renderer risks hit this brief's workloads:

- every glyph is re-uploaded each drawn frame;
- animating shader props, or `w`/`h` on a shaded node, allocates a params block per frame. That covers `$focus` scale plus a border, and NavDrawer width transitions.

Measure and report these. Do not fix them inside the renderer.

### The DOM renderer

`solid/src/core/dom-renderer` mirrors the renderer API, and the tests run on it (`SOLIDTV_DOM_RENDERING`). Any integration-API change must be made there too, so the test suite stays meaningful. That includes any new text-measurement API; it can measure with the browser.

## Text measurement and flex layout

This is a workstream across Solid and the renderer. **Review the alternatives before choosing one.** The comparison goes in the Checkpoint 1 design spec, with numbers from prototypes wherever a prototype is cheap.

### How it works today (verify)

**In Solid:**

- `flex.ts` (around line 32) gives up on the whole container pass when a text child has text but no `width` or `height` yet.
- Each text node's `_layoutOnLoad` (around `elementNode.ts:1151`) listens for `loaded`. On every load it schedules the post-mutation pass and also calls `parent.updateLayout()` synchronously, so one load can cause two flex passes. The listener is never removed.
- Text children are re-concatenated (`getText`) on every insert and update.

**In renderer v2 (spec §6.1, §10.2):**

- Text layout runs inside the scene pass, during the node's visit, once the font's description (metrics) has arrived. The atlas is not needed.
- `loaded { type: 'text', dimensions }` is queued and delivered between walks. Solid's flex then writes positions, which re-runs the walk (up to 3 walks).
- So a text whose size changes inside a flex container costs: a walk, the text layout, the event, a Solid flex pass, then a second walk.
- Layouts are cached in an LRU (`textLayoutCacheSize`, default 250), keyed by a string that `layoutKey` builds from the font id and every layout prop, on each lookup.
- After creation, `w` and `h` on a text node map to `maxWidth` and `maxHeight`.
- Check whether text that the walk does not visit (culled, hidden or alpha 0) is ever laid out. Solid's flex waits for its size.

### Alternatives to review

Measure each one, or reason it out with evidence when it is out of bounds. Record the rejected ones and why.

1. **The status quo:** event-driven, with two walks per text change in a flex container.
2. **A synchronous measurement API in the renderer**, usable as soon as the font description is loaded. For example, `renderer.measureText(props)` or a text node's `measure()`. It stores its result in the same `LayoutCache` the walk reads, so the walk reuses it. Solid could then run flex in its post-mutation pass before the walk: one walk, no `loaded` round trip.
3. **A width-only fast path** for single-line text with no wrapping: sum the advances, kerning and `letterSpacing` without building glyph runs. Per-font advance tables in typed arrays indexed by character code.
4. **Cheaper caching:**
   - cache keys that do not build a string per lookup;
   - a per-font map of text to width;
   - measurements shared across nodes. Virtual lists remount the same titles as you scroll.
5. **Dirty-tracked layout in Solid.**
   - Re-run flex only on the containers whose children changed size, propagated up the tree, instead of calling `updateLayout` from every `loaded`.
   - Skip the relayout when the measured size did not change.
   - Never let a text color or alpha change reach layout.
6. **Not waiting on text that cannot affect layout:**
   - text with a fixed `width` and `contain`;
   - `flexItem={false}`;
   - containers whose size and positions do not depend on that child.
7. **Before fonts load:** estimate sizes (for example, average advance × length) and correct them later, versus holding layout until fonts are ready. Apps usually preload fonts with `loadFonts` at startup.
8. **Flex inside the renderer's walk:** run layout during the scene pass. This touches `ScenePass`, so evaluate it on paper and write it up as a proposal only.
9. **Third-party layout engines** (Yoga via wasm or asm.js, and others). Check bundle size, support for Chrome 38 and 47, and the per-node interop cost. Rejection is likely, but record the numbers and reasons.

## Phase 2: rewrite the hot paths

Work scenario by scenario. For each change: measure before and after, keep it only if it beats the noise floor or removes allocations, and log the result in `docs/perf/log.md`.

### Leads from the 2026-10-03 survey (verify every one)

#### Key dispatch (`src/core/focusManager.ts`)

- **Allocations on every key event:**
  - a closure plus `runWithOwner`;
  - the `keyIdentities` array;
  - `performance.now()`;
  - `_pendingHistoryKey`, built even when history is off;
  - template-string handler names (`on${k}`, `onCapture${k}`, `on${k}Release`);
  - a `{ handled, lastHandlerSeen }` result object per bubble level.

  Intern handler names once per key.

- **Capture walk:** every press walks the whole focus path for capture handlers, even when none exist.
- **Handler storage:** handlers are per-instance expando props on varied hidden classes, so lookups are likely megamorphic.
- **`chainFunctions`:** allocates rest-args arrays.
- **`Config.focusDebug`:** not gated to dev builds.

#### Row and Column (`src/primitives/utils/handleNavigation.ts`, `withScrolling.ts`)

- **Per-press transition allocation:** each press allocates a `{ ...directional, ...base }` transition object and assigns it to `el.transition`.
- **Infinite loop bug:** `findFirstFocusableChildIdx` loops forever when `wrap` is on and every child has `skipFocus`.
- **`style` getter:** scrolling reads `style?.focus`, not `$focus`. The `style` getter allocates `{}` when no style is set.
- **`absX`:** the first scroll computes `absX`, which recurses to the root. In renderer v2, `absX` is O(depth).
- **Layout re-scroll:** a Row with a `selected` prop runs `scrollRow` on every layout.

#### Focus change

- **Every focus change schedules two runs.** `schedulePostMutation` (around `elementNode.ts:94`) registers `reprocessUpdates(runPostMutation)` and also `queueMicrotask(runPostMutation)`. Re-check this against v2's `reprocessUpdates` semantics: the callback runs after the walk and before the draw, and the walk re-runs, up to 3 times, if the callback writes.
- **`updateFocusPath`:**
  - walks every ancestor, including non-focusable wrappers;
  - lazily allocates a `States` object plus a bound callback per ancestor;
  - builds a fresh path array per change;
  - diffs the old and new paths with `indexOf`, which is O(depth²).
- **`States` extends `Array`:** `splice` and `slice` go through the species constructor, so each removal builds a new `States`, with `Object.entries`, `filter` and `map`.
- **Unbatched callbacks:** `onFocus`, `onBlur` and `onFocusChanged` run outside any batch, so signal writes inside user callbacks flush one at a time.
- **Two reactive flushes per change:** `setFocusPath`, and `Config.setActiveElement`.

#### Grid, Virtual and VirtualGrid

- **Spread re-runs:** a spread is one render effect over all props. A `cursor` or `focusedIndex` change re-runs the whole spread, which reallocates the handler closures and the `chainFunctions` closures.
- **Per-press slice allocation:** a `SliceState` and a slice array per press.
- **`List` diff cost:** inserting before an anchor does 2× `indexOf` plus `splice`, and `getNextSibling` is an `indexOf`.
- **At least two flex passes per press that moves the window.**

#### States and styles (`src/core/elementNode.ts`, `_stateChanged`; `src/core/states.ts`)

- **Change detection:** `set states` has no check for an unchanged value.
- **Recompute and re-apply:** every change recomputes all state styles and runs `Object.assign` over every key, with no diff, so every key goes through its setter.
- **Merging and undo:**
  - multi-state merging copies quadratically (`reduce` with spread);
  - undo allocates objects and closures;
  - `keyExists` uses `in`, which walks the prototype chain.
- **`forwardStates`:** overwrites the children's own states.
- **Shader props:**
  - `parseAndAssignShaderProps` allocates per call;
  - gradients create a new shader on every set;
  - a set with an `onAnimation.stopped` listener schedules a `setTimeout` per prop.
- **Direction to evaluate:** compile each static style object, including its `$state` blocks, once into a flat apply and undo plan, cached in a `WeakMap` keyed by the object. Then diff against the values last applied and write only what changed. Keep a slower path for inline literals and getter styles.

#### Layout (`src/core/flex.ts`, `flexLayout.ts`)

- **Allocations per pass:** an index array, 7 `Float32Array`s and a closure.
- **Unconditional writes:** every child's `x` and `y` are written even when unchanged, which can start transitions.
- **Production `console.warn`:** one remains.
- **Two implementations:** keep one, measured and tested, and delete the other. `flexLayout.ts` has no tests.
- **Text:** the text leads are in the Text measurement and flex layout section above.
- **Behaviour question for the user:** a `$focus` change to width or height does not reflow a flex parent today. Do not change this silently.

#### Nodes

- **`ElementNode` size:** an `ElementNode` has 24 underscore fields, plus an 11-key `lng` prop bag, plus expandos.
- **Renderer v2 handle shape:** v2 wants one heap object per node and a creation bag in fast mode. Unknown names written to the renderer handle change its hidden class, so never write them to the handle (spec §13.4).
- **Child list cost:** `insertChild`, `removeChild` and `cleanChildren` use `indexOf` and `splice`, and `cleanChildren` is O(n²).
- **Class fields:** class-field emit matters. HANDOFF measured renderer v2 node creation at about 1.3x slower than 1.10 with native class fields. Check what the demo app's build targets emit for `ElementNode`.

### Directions to evaluate (not mandates)

- Batch an entire key press into one reactive batch and one renderer update. That covers handlers, the focus-path change, state application, text measurement and layout.
- Keep focus and state bookkeeping in reused structures, with no per-press allocation.
- Bulk-apply props to the renderer from a compiled plan: either through the creation bag, or through a new post-creation bulk API on the renderer side if it measures faster.

Every route must render and navigate, and text-heavy screens must lay out as they do on arm B. Re-run `#/benchmark` and the Phase 0 suite across arms A, B and C.

## Checkpoint 2: final report to the user

Bring:

- the numbers for arms A, B and C per scenario, against the agreed targets;
- the allocations per press;
- the outcome of the text and flex work: the approach chosen, the walks and flex passes per text change before and after, and the cache hit rates;
- the contents of `MIGRATION-1.7.md`;
- the list of renderer commits, each with its measured gain;
- the renderer proposals you deferred;
- open risks, and what still needs device runs.

## Working rules

- **Use the Superpowers skills:**
  - `brainstorming` and `writing-plans` before code;
  - `test-driven-development`;
  - `subagent-driven-development` or `executing-plans` for the plan;
  - `systematic-debugging` for failures;
  - `verification-before-completion` before every claim that something passes or is faster.
- **Measure, don't guess.** No optimization ships without a before and after from the harness. A "faster" claim needs numbers from n≥3 runs that beat the noise floor.
- **Keep checks green** in `solid-1.7` at every commit: `npm test`, `npm run tsc` and `npm run lint`. In the renderer worktree, keep `pnpm test` green.
- **Small, focused commits**, ending with the attribution line the harness provides.
- **Stop and ask the user** before you:
  - add any app-facing break not approved at Checkpoint 1;
  - change focus or handler semantics or ordering;
  - change flex layout results, including when a `$focus` size change reflows its parent;
  - make any renderer change outside the integration surface and text measurement.
- **Fix real bugs** you find, such as the infinite `wrap` loop. Record each behaviour change in `MIGRATION-1.7.md`.
