# SolidTV 1.7 design: CPU per key press on renderer v2

Date: 2026-10-03
Status: **draft for Checkpoint 1**, for the user's review. Nothing here is
implemented yet. Phase 2 starts only after approval.
Brief: [2026-10-03-solid-1.7-rewrite-brief.md](2026-10-03-solid-1.7-rewrite-brief.md)

This spec proposes how to rewrite the hot paths of `@solidtv/solid` for 1.7.
It covers the architecture, the renderer integration and text-measurement
changes, the text and flex alternatives review, every app-facing change that
needs approval, and numeric targets per scenario.

The evidence is in `docs/perf/`:

- [README.md](../../perf/README.md): the benchmark harness and its method.
- [results/](../../perf/results/): the arm A and arm B numbers, raw and
  summarised.
- [survey-verification.md](../../perf/survey-verification.md): every lead from
  the brief's survey checked against the code, with a full trace of one key
  press.
- [text-flex-alternatives.md](../../perf/text-flex-alternatives.md): the text
  and flex alternatives review, with prototypes.

## 1. Summary

- **The lockstep port (arm B) costs more per key press than what ships today
  (arm A).** Renderer v2 makes frames cheaper (the demo's render pass: 89 →
  33 ms per run), but keydown-to-frame CPU on navigation presses is 1.25x to
  2.1x arm A's (6x throttle), and the demo app's `#/benchmark` press mean goes
  from 0.64 to 0.93 ms. Solid's code is the same in both arms, so the
  difference is how Solid drives renderer v2 (section 2.5).
- **Solid's own work per key press is small but allocates every time:** about
  1.9 KiB of framework allocations and 0.8 KiB of reactivity per Row press,
  15 KiB per NavDrawer toggle, 12 KiB per details-panel press. The target is
  zero framework allocations in the steady state.
- **Text in flex costs two walks per frame** on every text scenario, and flex
  runs once per relaid text (7 passes per details-panel press, 42 per 20-tile
  mount). The proposed synchronous text measurement (section 4a) brings this
  to one walk and one pass per affected container.
- **The demo app's production build makes renderer v2 allocate per visited
  node per frame (confirmed).** Terser (the demo's settings: compress on)
  inlines the renderer's single-use world-transform helper into the walk as
  an IIFE (`!function(s, id, parent){…}(…)` inside `ScenePass.visit`). With
  `compress: { reduce_funcs: false }` the IIFE is gone and the renderer's
  allocations per press drop from 56.7 to 3.4 KiB (rows-ud-auto) and from
  67.7 to 8.6 KiB (virtual-grid). The fix is one line in an app's build
  (proposed for the demo app in Phase 3, and for the docs), and a renderer
  proposal so no bundler can do it (`renderer-proposals.md`, P3).
- **B's extra press cost is in the tail, not the typical op:** the median
  press is about equal on A and B; the profiles put the difference in Solid's
  reads of renderer v2 props through megamorphic accessors (top cost 2) and
  in `animateProp` restarts.

## 2. Baseline numbers (arms A and B)

Method: [docs/perf/README.md](../../perf/README.md). Headless Chromium 141
with the hardware GPU (ANGLE Metal, Apple M4 Pro), 5 µs clock, each scenario
built per arm with the demo app's modern-bundle settings and its flex engine
(`flexLayout.ts`). The generated summary, at 6x CPU throttle (the brief's TV
proxy): [results/2026-10-03/summary.md](../../perf/results/2026-10-03/summary.md);
the profile digest: [profiles.md](../../perf/results/2026-10-03/profiles.md).
The raw per-run JSON is regenerated by `npm run bench` and not committed.

**Noise floor.** B and C are the same code today, so C/B is the in-session
noise: at 6x it spans 0.74-1.22 on per-op totals. CDP throttling is a duty
cycle (about 0.17 ms running, 0.85 ms suspended), so a sub-millisecond op
reads either unthrottled or one suspension longer; per-run means over 60-90
ops still carry about ±0.05 ms. Effects under about 25% at 6x are not
results at n = 3; Phase 2 uses n ≥ 5 near the floor, and the pooled per-op
medians below for typical-op comparisons.

**The typical press versus the mean.** Pooling every op of the 3 runs and
taking the per-op median (which, for ops shorter than the throttler's 0.17 ms
slice, approximates full-speed CPU at the clock's 5 µs resolution), a Row
press is about the same on A and B: 50-75 µs total (rows-lr-noshift 55 vs 50,
rows-lr-auto 70 vs 75, rows-ud-auto 75 vs 80). So B's higher means come from
the tail of expensive ops, which is what drops frames on a TV: the profiles
below put it in the dispatch and navigation code reading renderer v2 props,
and in GC. An unthrottled (1x) series was also run and is **not usable** on
this Mac: an idle page's main thread runs on an efficiency core or at a low
clock, so every op read about 5x slower than at 6x (recorded in
`docs/perf/README.md`).

## 3. Architecture

The rewrite keeps every public name and the compatibility contract pinned by
the Phase 1 tests (section 6). It changes how the work is done, not what it
does. Every item below is measured before and after with the harness and
logged in `docs/perf/log.md`; an item that does not beat the noise floor or
remove allocations is dropped.

### 3.1 Key dispatch (`focusManager.ts`)

Today, per key event (keydown **and** keyup): a closure plus `runWithOwner`, a
`keyIdentities` array, 2 to 4 template-string handler names, a result object
per bubble pass, a `_pendingHistoryKey` object even with history off, and a
capture walk over the whole focus path. The keyup repeats all of it, plus a
full bubble walk for `on<Key>Release` handlers that almost no app has.

Proposed:

1. **Interned handler names.** One table per mapped key name, built when the
   key map is set: `{ on, onCapture, onRelease, onCaptureRelease }`. Unmapped
   keys fall back to a small cache keyed by `e.key`.
2. **Skip walks that cannot find a handler.** Solid's `setProperty`
   (`solidOpts.ts`) sees every prop name once, when it is set. It raises
   module flags the first time a name starting with `onCapture` or ending with
   `Release` is set on any node. With no capture handler anywhere, the capture
   walk is skipped; with no release handler anywhere, the keyup bubble walk is
   skipped. Semantics are unchanged: a walk that could find a handler still
   runs, in the same order.
3. **No per-event allocation.** One reused bound listener instead of a
   closure per event, no `keyIdentities` array (two locals), a reused result
   record, and the history record built only when `Config.focusHistoryDebug`
   is on.
4. Unchanged: handlers keep `this` bound to the node, `true` stops
   propagation, the capture → bubble → `onKeyPress` order, and `runWithOwner`
   (it is what makes a key handler's signal writes flush once, after the
   handler).

### 3.2 Focus change (`updateFocusPath`)

Today: a walk of every ancestor to the root, `states.has` on an `Array`
subclass per ancestor, an O(depth²) `indexOf` diff against the previous path,
a fresh path array, one `States` species construction per blur (`splice` on
an `Array` subclass builds a new `States`), and every `onFocus`, `onBlur` and
`onFocusChanged` callback outside any batch, so each signal write in a callback
flushes on its own. Then two more reactive passes: `setFocusPath` and
`Config.setActiveElement`.

Proposed:

1. **Generation-stamped diff.** Each focus change takes a new generation
   number; the walk up from the new leaf stamps each ancestor; the old path's
   nodes without the new stamp are the ones that lost focus. O(depth), no
   `indexOf`.
2. **Two path arrays, swapped.** `focusPath()` still returns a fresh array to
   readers that hold on to it: the signal gets a copy only when something
   reads `focusPath` (a cheap `slice` of a handful of nodes), and the internal
   diff uses the reused buffers.
3. **`States` without species allocation.** `static get [Symbol.species]()`
   returns `Array`, and `remove` shifts in place instead of `splice`. `has`
   keeps matching `focus` against `$focus`.
4. **One reactive flush per focus change (needs approval, section 5.1).** Run
   the focus phase (the callbacks, `setFocusPath`, `Config.setActiveElement`)
   inside one `batch`. The callbacks run in exactly today's order; what
   changes is that effects triggered by their signal writes run once, after
   the last callback, instead of after each write.

### 3.3 States and style application (`_stateChanged`, `states.ts`)

Today every state change recomputes every active state's block, merges them
with object spread (quadratic for several states), builds an undo object and
closures, and `Object.assign`s every key through its setter, changed or not.
A `border` value is re-parsed into `border-*` keys on every apply (about 11
allocations per border write), and each facade write in renderer v2 allocates
a vec4 and repacks the shader params even when the value is unchanged.

Proposed, a **compiled style plan**:

1. When a style object is first applied, compile it once into a plan, cached
   in a `WeakMap` keyed by the object: for each `$state` block, a flat list of
   (key, value) entries with `border`/`shadow`/`borderRadius` already expanded
   into their shader keys. Static module-level styles (the common case)
   compile once per app.
2. Each node keeps, in one lazily allocated record, the values it last applied
   per key. A state change resolves the target value for each key that any
   active or previously active state touches (in `stateOrder` precedence, then
   undo falling back to `theme`, then `style`, exactly as today) and writes
   only the keys whose value is not `===` the last applied value.
3. `set states` with an unchanged value does nothing.
4. Slower path, same results: inline literals (re-created every render) and
   styles with getters (`get color()`) are not cached; they are compiled per
   apply, and getters are read at the same moments as today (pinned by
   `contract-styles.test.tsx`).
5. `forwardStates` keeps its semantics (it overwrites the children's states,
   pinned), without the `slice` per change.

### 3.4 Flex layout (`flex.ts`, `flexLayout.ts`)

Today: two implementations (the default build runs `flex.ts`; the demo app
sets `VITE_USE_NEW_FLEX=true` and runs `flexLayout.ts`), an index array, 7
`Float32Array`s and a closure per pass, every child's `x`/`y` written even when
unchanged, a production `console.warn`, and a pass that bails out whenever a
text child has no size yet.

Proposed:

1. **One implementation** (needs approval, section 5.3): keep `flexLayout.ts`
   (it is what the demo app runs, and the only one that supports array
   `padding`, per-side padding and the `margin` array), fixed where the Phase
   1 tests found it wrong, and delete `flex.ts` and the env switch.
2. **No allocation per pass:** module-level scratch typed arrays grown on
   demand, no closure, children walked by index.
3. **Write only what changed:** compare before writing `x`, `y`, `w`, `h`, so
   a relayout that moves nothing writes nothing (and starts no transition).
4. **Dirty-tracked, depth-ordered queue:** a container is queued when a
   child's size changes; the queue runs deepest first; a container propagates
   to its parent only when its own size changed. Target: one flex pass per
   affected container.
5. **Text sizes before flex** (section 4): flex never bails on a text whose
   font description is loaded.
6. Unchanged (needs approval to change, section 5.4): a `$focus` change to a
   flex child's width or height does not reflow its parent.

### 3.5 Post-mutation scheduling

Today every `schedulePostMutation` registers both `reprocessUpdates(run)` and
`queueMicrotask(run)`. The microtask run does the work; the in-frame run is a
no-op that still requests a frame. Proposed: the microtask only, plus
`reprocessUpdates` only for the one-shot text fallback while a font
description is missing (section 4). The three phases (delete flush, layout,
focus) keep their order.

### 3.6 Nodes (`elementNode.ts`, `solidOpts.ts`)

1. **Never write unknown names to the v2 handle.** Today text-only props
   written to a rendered `<view>` (`fontSize`, `lineHeight`, `maxWidth`,
   `text`, `contain`, `fontFamily` through the `fontWeight` setter) become own
   fields of the renderer handle, and the shader facade grows `border` and
   `shadow` fields. These are routed to the `ElementNode` instead (bug fix,
   no visible change).
2. `absX`, `absY` and `destroyed` leave the forwarded setter list (they are
   getter-only on v2, and writing them throws today).
3. **Child list:** `insertChild(before)` and `removeChild` scan from the end
   (Solid appends and removes at the tail most often), and `cleanChildren`
   becomes O(n).
4. **Draw order** (bug): Solid's `insertChild(node, before)` and same-parent
   moves never reorder renderer siblings, and v2 draws in sibling order. With
   a renderer `insertBefore` (section 4), Solid keeps the renderer's sibling
   order equal to `children`. This matters for overlapping siblings of equal
   `zIndex`: a scaled `$focus` tile in a Virtual row, or a `<Show>` before an
   anchor.
5. `ElementNode` keeps one fixed shape at construction (already true: it has
   no class fields and 27 own assignments). `TextNode` and `States` have class
   fields that compile to `_defineProperty` calls under the solid tsconfig's
   ESNext target; they become constructor assignments.
6. **Monomorphic prop accessors** (top cost 2). Today every forwarded prop's
   getter and setter is the same function body (`this.lng[key]`,
   `this.lng[name] = value`) created in a loop, so one feedback vector sees
   every prop name: the access is megamorphic, and into v2's prototype
   accessors it is also a call V8 does not inline (a returned double is
   boxed). Proposed: one accessor per prop with a constant property name
   (written out, or generated once at module load from a small table), and
   the scroll and flex code reads each prop once into a local. Measured in
   Phase 2 against the generated-loop version on arms B and C; kept only if
   it beats the noise floor.

### 3.7 Primitives

1. **Row and Column** (`handleNavigation.ts`, `withScrolling.ts`): no
   transition object per press (the merged forward and backward transitions
   are cached per base transition), the scroll reads its inputs once into
   locals, and the infinite loop with `wrap` and every child `skipFocus` is
   fixed (bug).
2. **Virtual and VirtualGrid:** the spread is split so a `cursor` or
   `focusedIndex` change re-runs only the props that depend on it; the
   per-press `SliceState` is reused; `style?.focus` becomes `$focus` (bug: the
   focus scale was never seen); a window shift costs one flex pass.
3. **Grid:** its 5 handlers stop being re-created on vertical moves.

### 3.8 What stays as it is

- The universal-renderer exports and the compiler contract.
- `runWithOwner` around key handlers.
- The undo rule (theme, then style; JSX props are not restored).
- `forwardStates` overwriting children's states.
- Text before fonts load: layout holds until the font description arrives
  (estimates are 13% to 26% off; rejected).

## 4. Renderer integration and text measurement

All renderer changes stay inside the brief's boundaries (the surface Solid
touches, and text measurement). Each is one focused commit in
`renderer-v2-solid`, with a measured gain from a Solid benchmark, `pnpm test`
green, and updates to `publicApi.test.ts` and `docs/upgrade-1.x-to-2.0.md`.
The DOM renderer (`src/core/dom-renderer`) gets the same API, so the jsdom
suite stays meaningful.

| #   | Renderer change                                             | Boundary                         | Why                                                                                                      | DOM renderer mirror                                                              |
| --- | ----------------------------------------------------------- | -------------------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| R1  | `TextNode.measure(): boolean`                               | text measurement; node accessors | lays the text out now into the shared `LayoutCache`, so Solid's flex runs before the walk: 1 walk, not 2 | `DOMText.measure()`: synchronous `getBoundingClientRect` when the font is loaded |
| R2  | Text-keyed `LayoutCache` (no `layoutKey` string per lookup) | text measurement                 | 0.02 µs and 0 B per hit, against 0.36-0.71 µs and about 1 kB                                             | n/a                                                                              |
| R3  | Typed-array advance and kerning tables in the line breaker  | text measurement                 | 3.2× (title) and 2.3× (description) faster breaking, bit-identical in 17,100 cases                       | n/a                                                                              |
| R4  | Public `insertBefore(node, before)` on the node API         | node accessors                   | keeps draw order equal to Solid's child order (bug fix)                                                  | DOM `insertBefore`                                                               |
| R5  | (if it measures faster) a post-creation bulk-set API        | node accessors                   | apply a compiled style plan in one call instead of one setter per key                                    | a loop of setters                                                                |

R5 is evaluated, not assumed: v2 setters already only store and mark, so a
bulk call saves only the per-call dispatch. It ships only with a measured win.

Proposals outside the boundaries go to `docs/superpowers/specs/renderer-proposals.md`
(not implemented): layout inside the scene pass (rejected for 1.7, see the
review), and the two known open risks this brief's workloads hit, which are
measured and reported but not fixed: every glyph re-uploaded each drawn frame,
and a params block allocated per frame for animated shader props or sizes.

## 4a. Text measurement and flex: alternatives and recommendation

The full review, with method, prototypes and numbers, is
[text-flex-alternatives.md](../../perf/text-flex-alternatives.md). Summary:

**How it works today (verified on arm B, real WebGL).** A text change inside a
flex container costs **two scene walks** in its frame: walk 1 lays the text
out and queues `loaded`; Solid's handler runs a flex pass between the walks;
the flex writes force walk 2, which re-emits every visible quad and glyph.
Flex runs **once per relaid text**, not once per container: one press of the
details-panel shape ran 12 flex passes over 4 containers. Text under a culled
ancestor (out of bounds or alpha 0) is never laid out, so its flex container
stays unlaid until it scrolls into the bounds margin (arm A gates text layout
the same way). The `loaded` listener is never removed and fires on every
relayout even when the size is unchanged.

| #   | Alternative                                                       | Verdict                                                        | Evidence                                                                                                                                                                                                    |
| --- | ----------------------------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Status quo, event-driven                                          | Rejected                                                       | 2 walks per text change, 1 flex pass per relaid text (12 for 4 containers), containers under culled ancestors unlaid                                                                                        |
| 2   | Synchronous `TextNode.measure()` filling the walk's `LayoutCache` | **Adopt** (prototyped: ~60 renderer + ~45 Solid lines)         | details panel: walks 2 → **1**, `loaded` 6 → **0**, flex passes 12 → 5 (4 with item 5), layouts in the walk 6 → 0, **identical final positions**                                                            |
| 3   | Width-only fast path for single-line text                         | Reject as a separate path; adopt its tables inside the breaker | a measured text that is also drawn would be laid out twice; the typed-array advance and kerning tables inside `mapTextLayout` are 3.2× (title) and 2.3× (description) faster, bit-identical in 17,100 cases |
| 4   | Cheaper cache keys                                                | **Adopt** a text-keyed cache                                   | 0.02 µs and 0 B per hit against 0.36-0.71 µs and ~1 kB of garbage for the `layoutKey` string; the cache is already shared across nodes by content                                                           |
| 5   | Dirty-tracked flex in Solid                                       | **Adopt** a depth-ordered queue and an unchanged-size skip     | one pass per affected container; a 20-tile row pass costs 7-12 µs desktop on the real stack and ~2.1 kB of heap                                                                                             |
| 6   | Not waiting on text that cannot affect layout                     | Adopt the `flexItem={false}` fix only                          | today an unsized `flexItem={false}` text blocks its whole container (bug)                                                                                                                                   |
| 7   | Estimate sizes before fonts load                                  | Rejected: hold, as today                                       | average-advance estimates are 13-26% off; every correction moves siblings visibly                                                                                                                           |
| 8   | Flex inside the renderer's walk                                   | Rejected for 1.7 (paper only); `renderer-proposals.md`         | touches `ScenePass` and `NodeStore` (out of bounds), breaks one-pass-per-frame for content-sized containers, and gains nothing over 2 + 5 on walk count                                                     |
| 9   | Yoga, Taffy, css-layout                                           | Rejected                                                       | yoga 3 and taffy are wasm (Chrome 57+); the asm.js yoga build is 365/80 kB min/gzip and unmaintained; css-layout has no `gap` and different semantics                                                       |

**Recommendation: 2 + 3 (tables in the breaker) + 4 + 5 + 6, and hold before
fonts.** Expected per text change in a flex container: **1 walk, 0 `loaded`
events (when the app has no listener), 1 flex pass per affected container, 0
layouts in the walk**, a cache hit at 0.02 µs and 0 B. Solid measures in its
post-mutation pass, before flex, with no persistent `loaded` listener and a
one-shot fallback while a font's description is missing; writes to a
layout-affecting text prop queue the flex parent. The DOM renderer gets a
synchronous `measure()` (`getBoundingClientRect` when the font is loaded).
Line breaking stays identical to 1.10 by construction: `measure()` calls the
same `layoutText`.

Risks: a layout-affecting write that bypasses Solid's setters (a raw
`el.lng.fontSize`, a renderer animation of `fontSize`) leaves flex stale, so a
dev-only warning listener is proposed; flex writing a text's `width` can loop
measure → flex (bounded, needs a test); eager measuring adds pressure on the
250-entry layout cache (a browse page of 7 rows × 20 tiles × 2 texts is 280
layouts), measured by the `text-flex-mount-new` and `text-virtual-row`
scenarios before the default changes.

## 5. Changes that need the user's approval

Nothing below is implemented. Each item lists what changes for apps, the
demo-app files it touches, and the expected gain (measured before and after in
Phase 2; an item whose gain does not beat the noise floor is dropped). Approved
items go into `MIGRATION-1.7.md` with their measured numbers.

### 5.1 One reactive flush per focus change (timing of effects)

- **What changes:** the focus phase runs inside one `batch`. `onFocus`,
  `onBlur` and `onFocusChanged` still run in today's exact order, and memos
  read inside them are still current (Solid recomputes a stale memo on read).
  What moves: an effect (`createEffect`, a JSX binding) triggered by a signal
  written in one of these callbacks runs after the last callback of the change
  instead of right after the write. Same microtask, before the frame, so
  nothing visible changes; code that writes a signal in `onFocus` and then
  reads a node prop that an effect sets from it, in the same callback chain,
  would see the old value.
- **Demo app:** every `onFocus`/`onFocusChanged` that sets a signal
  (`Portal.tsx`'s tiles, the NavDrawer). Key handlers are unaffected: they
  already run inside `runWithOwner`, which batches.
- **Expected gain:** today each signal write in a callback flushes on its own,
  plus two more passes for `setFocusPath` and `Config.setActiveElement`. The
  `portal-focus-text` scenario measures it.

### 5.2 Eager layout of text under culled ancestors

- **What changes:** with `measure()` (section 4a), a flex container's text is
  laid out at mount or on change even when an ancestor is out of bounds or at
  alpha 0, so the container has its size before it is shown. Visible results
  are identical; a container that was never visited is now laid out (today it
  stays unlaid, and an app that reveals content once a text has its size could
  wait forever).
- **Cost:** about 2 µs desktop per extra title at mount (a 20-tile row lays
  out 20 more texts), more pressure on the 250-entry layout cache, and text
  in hidden `KeepAlive` pages is laid out while hidden. The alternative keeps
  laziness and the second walk when such a container scrolls into view.

### 5.3 One flex engine

- **What changes:** keep `flexLayout.ts` (what the demo app runs through
  `VITE_USE_NEW_FLEX=true`, and the only engine with array `padding`,
  per-side padding and the `margin` array); delete `flex.ts` and the switch.
  Apps on the default build (`flex.ts`) see different results only where the
  two differ today (pinned in `contract-flex.test.tsx`): cross-axis padding,
  array padding (`flex.ts` produced `NaN` positions), the `margin` array,
  `flexWrap` with padding, `wrap-reverse` (wrong in both), and a production
  `console.warn` on `flexGrow` with no free space.
- **Fixes folded in** (5.8, layout results): `flexLayout.ts` offsets
  cross-axis `center`/`flexEnd` by `paddingTop` against the full size (a
  centred badge text sits 10 px low and overflows); `justifyContent: center`
  with padding is off-centre by the padding (both engines).
- **Gain:** one engine to measure and keep allocation-free; bundle size
  (`flex.ts` is about 330 lines).
- **Alternative:** keep both, and rewrite both. Twice the work, and the
  default-build engine stays the one the demo app does not exercise.

### 5.4 A `$focus` width or height change does not reflow its flex parent

Today it does not (confirmed, pinned). **Proposed: keep it.** Reflowing would
add a flex pass to every focus change that touches a size, and change layout
results for apps that rely on the focused tile overlapping its neighbours.
Say if you want an opt-in.

### 5.5 The hold contract in the brief does not exist

The brief's contract lists `on<Name>Hold` handlers and
`useFocusManager(keyMap, { userKeyHoldMap, holdThreshold })`. Both were removed
in 1.5.1 (commit `78f5fde`, #49) in favour of `useHold`; arms A and B have
neither. The second argument of `useFocusManager` is now a key-event source;
an object without `addEventListener` is ignored. The demo app still passes
them (`App.tsx:5, 32-38`, `KeyHandling.tsx:49`), imports `KeyHoldMap` from
`@solidtv/solid/focusManager` (an export that does not exist and a type that
was removed), and so its EnterHold and BackHold never fire on 1.6.4.
**Decision needed:** (a) the contract is today's behaviour (`useHold`), and
Phase 3 ports the demo's hold handlers to `useHold`; or (b) restore
`on<Name>Hold` and the options object. Recommended: (a).

### 5.6 Absorbing renderer breaks in Solid

The brief asks Solid to absorb a renderer break where a few lines can.
Proposed, off the hot path:

- `renderer.stage.shManager` keeps working: Solid defines it on the renderer
  object at `createRenderer` as a getter returning the renderer (which has
  `registerShaderType` and `createShader`), with a dev-only deprecation
  warning. The renderer object is one per app, not a node handle. Hits
  `src/index.tsx:213` in the demo app.
- `renderEngine` and `fontEngines` in `Config.rendererOptions` are dropped by
  Solid before it builds the renderer, with a dev warning. The imports of
  `@solidtv/renderer/webgl` and `/canvas` cannot be absorbed: they fail at
  module resolution.

### 5.7 Kept as today (no approval needed, listed so it is explicit)

- The undo rule: for each key the last state application wrote, undo writes
  `theme[key]`, else `style[key]`, else `undefined`; JSX values are never
  restored.
- `forwardStates` overwrites the children's own states.
- A reactive `states` string or array replaces the list, dropping a `$focus`
  the focus manager added.
- `onSelectedChanged` fires twice on an autofocus mount (Row, Column,
  VirtualGrid, Grid with `selected`). Fixing it changes callback counts; say
  if you want it fixed.
- VirtualGrid's `onSelectedChanged` is called as `(idx, grid, active,
lastIdx)`, not the brief's `(idx, col, elm)`.
- `states.slice()` and other `Array` methods on `states` return a plain
  `Array` instead of a `States` (a side effect of 3.2.3; nothing in Solid or
  the demo app relies on it).
